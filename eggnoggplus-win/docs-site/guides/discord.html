Discord, LFG, and yule:// links

The server can post queue messages through the LFG bot, and the game can publish local Rich Presence. Both integrations are optional.

Safe deep-link routes

yule://hub
yule://requests
yule://queue/casual
yule://queue/competitive
yule://challenge/player_1

Equivalent arguments are --online, --requests, --queue=casual, --queue=competitive, and --challenge=player_1. Challenge targets are canonical lowercase account names.

The installer may register the protocol per Windows user. Routes reject unknown/doubled/encoded paths, queries, fragments, userinfo, credentials, endpoints, match ids, and tokens. Queue/request/challenge intent waits for authentication and resumes after remembered or manual login. Pending intent expires after two minutes or when the hub closes.

Existing-process delivery

Only protocol activations are single-instance. The first game owns a per-login-session Windows message broker. A later valid protocol launch forwards its already parsed intent, foregrounds the existing game, and exits before SDL video creates another window. Normal executable launches may still open a second instance for local testing.

A link received during setup/gameplay stays pending and cannot force a forfeit. Every launch normalizes the working directory to the installed executable, so browser/shell callers do not create stray data, mods, logs, or dumps elsewhere.

LFG message lifecycle

  • Only an authenticated player who remains in a public Casual/Competitive queue for two seconds gets a post.
  • Direct friend challenges never post. Duplicate joins never duplicate a post.
  • The Join queue button is left; Challenge player is right.
  • Leave, queue change, match, disconnect, and orderly shutdown edit the exact message in place and remove both buttons.
  • A “Match found” edit remains for 24 hours by default, then is deleted. Other inactive history remains.
  • An uncatchable machine/process kill can leave a harmless stale public post; remove it manually after recovery.

The integration uses outbound Discord REST only: no Gateway, intents, slash commands, incoming bot port, or additional matchmaking authority.

Discord bot and service setup

  1. Create/select the application, open its Bot page, and obtain the bot token.
  2. Copy the LFG channel id with Discord Developer Mode.
  3. Install only the bot scope with permission integer 19456: View Channel, Send Messages, Embed Links.
  4. Create a root-owned mode-0600 file such as /etc/eggnogg/lfg.env.
DISCORD_LFG_ENABLED=1
DISCORD_LFG_BOT_TOKEN=replace_with_secret
DISCORD_LFG_CHANNEL_ID=123456789012345678
DISCORD_LFG_PUBLIC_BASE_URL=https://example.com/yule
DISCORD_LFG_POST_DELAY_MS=2000
DISCORD_LFG_MATCH_DELETE_MS=86400000
LFG_REDIRECT_HOST=127.0.0.1
LFG_REDIRECT_PORT=47880

Add EnvironmentFile=/etc/eggnogg/lfg.env in a systemd drop-in for the existing online service, daemon-reload, and restart. The LFG bridge and redirect run inside that same Node process; do not create a separate daemon.

Never run systemctl show ... -p Environment while sharing troubleshooting output—it prints the bot token. Rotate the token immediately if it enters chat, source control, logs, screenshots, or shell history.

Expose only strict HTTPS handoff routes

Keep port 47880 loopback-only. Proxy exact completed routes without swallowing the existing updater subtree:

location ~ "^/yule/(?:hub|requests|queue/(?:casual|competitive)|challenge/[a-z0-9_]{1,24})$" {
    proxy_pass http://127.0.0.1:47880;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto https;
}

If a broad location ^~ /yule/ exists, narrow it to /yule/releases/ or use exact LFG route locations. The redirect accepts only GET/HEAD. Browser GET launches the safe protocol, waits, attempts window.close(), then shows a manual-close/link fallback when policy prevents closing. HEAD is a no-store 302 for probes.

Verify LFG end to end

curl -I http://127.0.0.1:47880/yule/hub
curl -I https://example.com/yule/hub
curl -I https://example.com/yule/queue/casual
curl -I https://example.com/yule/releases/latest.json
sudo ss -ltnp | grep 47880

Expect exact Location: yule://..., Cache-Control: no-store, a still-working updater manifest, and a listener on 127.0.0.1 only. Then test sub-two-second leave, both queue types, duplicate join, queue switch, direct challenge (no post), disconnect, immediate match, 429 retry, clean restart, both buttons, login-resume, existing-instance delivery, and one-day matched deletion.

Configure Discord Rich Presence

# mods/modframework.cfg
discord_application_id=1531027934004117664
discord_presence=1
discord.app
discord.app 1531027934004117664

The public numeric application id is not a secret. Release builds compile the shown Yule ID and default presence on even without a config file; blank or invalid stale overrides preserve that default. The command validates/persists a valid override and reconnects without restarting. Toggle presence from Mods → Framework or Online Settings.

Published classes are fixed: menus, local match, hub, signing in, friends/challenges, casual queue, competitive queue, prematch, and casual/competitive/friend online match. No usernames, opponents, maps, ratings, ids, endpoints, tokens, buttons, parties, or join secrets are included.

The dependency-free client talks only to Discord's local Windows named pipe using overlapped bounded I/O. It rate-limits/coalesces updates, reconnects every 15 seconds, and never waits for Discord or performs network access. An offline-looking bot presence is normal for the outbound-REST LFG bot and unrelated to local Rich Presence.

Privacy boundary

The LFG bot receives only canonical public username and queue name. Mentions are disabled. It must never receive ratings, match ids, server/control/P2P endpoints, credentials, rendezvous data, session tokens, packet-auth tokens, or direct-match links. Rich Presence receives only a closed local activity enum.

Inspect Discord payload tests and service logs before every release. The HTTPS bridge is a user-confirmed handoff, not a private authentication channel.
