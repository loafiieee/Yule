Online multiplayer

The public flow is account → queue or friend challenge → hidden deterministic setup → authenticated direct UDP or relay → rollback match → confirmed result. Players never need to expose host/join details.

Before you connect

  • Both players need the same compatible game/framework build and required online protocol revision.
  • Both need the server-selected map package, including identical external PNG and optional map.lua bytes.
  • The control server must advertise control protocol 3, match protocol 4, P2P protocol 17, packet authentication, social controls, private rematch, and relay.
  • Allow the game through Windows Firewall. The default server is eggnogg.loafiieee.com:47778 using TCP control and UDP rendezvous/relay on the same port.
  • Leave the local P2P port on Auto unless you have a deliberate network rule.
A new client paired only with old clients/server revisions is expected to fail compatibility checks. Test updated client-to-updated client against the matching deployed server before diagnosing NAT.

Use the online hub

Open ONLINE from the main menu or run online.hub.

Play
Register/login, optional Remember me, public Elo, Casual Queue, Competitive Queue, and queue leave/status.
Friends
Add friends, view requests/presence, select a mutually installed map, send/accept/decline five-minute challenges, mute challenge notifications, block/unblock, and unfriend.
Settings
Server host:port, local UDP port, challenge notifications, and optional Discord Rich Presence.

Remembered credentials use Windows Credential Manager. The config file stores only username and preference, not the password.

What happens after “match found”

  1. The server selects a map from the intersection of both complete client manifests, assigns player slots/seed, and supplies fresh rendezvous and packet-auth material.
  2. Both clients attempt the same server-selected route generation and exchange authenticated HELLO packets.
  3. The native match, exact map/content/script, synchronized reset, rollback layout, initial state, built-in palette tuple, and neutral frame zero are prepared during the countdown.
  4. Each client sends READY only after frame zero is restorable and the layout proof matches.
  5. The server commits gameplay only after both clients are ready. Pre-commit failure is a no-contest setup abort.

Normal completion is confirmed only when both clients report the same winner. Leaving a committed match is an explicit forfeit. The native win animation stays visible; the hub opens only after Eggnogg returns to main. A private rematch is an explicit bilateral vote, expires after 45 seconds by default, is unranked, and revalidates the previous map.

Direct P2P and relay

The server selects loopback, LAN, or public candidate routing. Both peers probe symmetrically; host/join assigns player and initial-state authority, not a privileged gameplay host. P2P v17 applies per-match HMAC-SHA-256 authentication (128-bit tag), role/session binding, and a 4,096-packet replay window.

If direct traversal cannot establish after a fresh socket generation, the server moves both clients to its bounded relay. Relay admission is limited to that active match's observed endpoints, assigned slots, packet types/sizes, and rate budgets. End-to-end peer authentication still applies through the relay.

P2P packets are authenticated, not encrypted. The relay/control server can observe metadata; the raw TCP account/control channel currently lacks TLS.

Compatibility and mods

Each client map_manifest includes its informational framework_version, strict integer control/match/P2P versions, and deterministic build_id, game_exe_id, and framework_dll_id fingerprints. The client requires cap_client_build_gate: 1 before login. The server admits only the exact 3/3/17 tuple and pairs only clients whose three build fingerprints also match; missing, malformed, old, or mismatched values fail before a match is created. P2P v16 and v17 are intentionally incompatible because both the authentication-key domain and packet layout changed. The release label is logged for diagnosis, but is not itself the compatibility gate. Server registration logs include [maps] ... build=... exe=... dll=... protocols=3/3/17, and match creation logs the checked build plus the selected P2P version.

Map keys include package metadata, room text, external V2 assets, and optional script bytes. Numeric map selectors are local and must never be compared across installations.

Gameplay-affecting Lua mods are suspended from match assignment through cleanup. Read-only/cosmetic mods can remain active. The framework build/map/layout identifiers catch ordinary incompatibility but are not cryptographic anti-cheat reports from a trusted authority.

Run the active troubleshooter

online.troubleshoot

Leave the console open for up to five seconds. The test runs without pausing the game and checks:

  • TCP reachability to the configured control server;
  • UDP ping/pong plus server-observed public address and port;
  • the Windows adapter actually selected for the route to that server;
  • VPN/tunnel-like adapter evidence and local private/CGNAT address ranges.

A Radmin, Tailscale, VPN, or tunnel adapter may be listed as active without being the server route. VPN detection is heuristic. A private LAN address proves ordinary NAT, not CGNAT; compare the router's WAN IPv4 to the public IPv4 reported by the UDP test. A local address in 100.64.0.0/10 is stronger CGNAT evidence.

Capture a secret-free snapshot

net.diag
console.copy output

Run it during the failed connection, not only afterward. It prints server state, active match, selected route and attempt, local UDP port, peer/candidate status, packet counters, rollback/prediction/correction state, and a verdict without credentials or tokens.

Also collect mods/modframework.log, the corresponding server log window, and both peers' timestamps. Look for mismatched route generations, one-sided READY, protocol rejection, layout mismatch, missing UDP probes, relay activation, and premature control disconnect.

Developer host/join and rollback probes

These commands are debugging tools, not the public hub flow:

ggpo.roundtrip
ggpo.loopback on
ggpo.local on

# Copy the same 64-hex key on each machine, then:
ggpo.net key
ggpo.net host 47777
ggpo.net join 192.0.2.10 47777

ggpo.net sim 5 2 8
ggpo.net status
ggpo.net off

ggpo.net key consumes and clears the clipboard; it never writes the key into history/logs. F2 runs roundtrip, F3 loopback, F4 local session, and F6/F7 the armed debug host/join path.

Small match network HUD

Online > Settings > Match Network HUD is off by default. When enabled, active gameplay and paused Options show one muted top-right line with smoothed round-trip ping, local input delay, and cumulative rollbacks. The console controls the same persisted setting with ggpo.net hud [on|off].

The ping is the existing service-tick estimate converted at approximately 60 Hz. It is useful for a quick sanity check, but it is not sequence-aware jitter, loss, stall, or route telemetry.

Current production limitations

  • The account/control TCP channel has no TLS or certificate validation.
  • Result authority still relies on client reports; ranked-grade authoritative validation is unfinished.
  • The LAN-only maintenance UI covers password reset, ban/unban, disconnect, rating reset, and live counts. Durable database storage, audit logs, account deletion, granular admin roles, monitoring, and key rotation remain incomplete.
  • IPv6, established-match reconnect/rebinding, adaptive mid-match route failover, production GGPO integration, and broad two-machine/NAT soaks remain open.
  • Compatibility reports and Lua suspension are not anti-cheat against a modified native client.

See security & limitations before operating a public server.
