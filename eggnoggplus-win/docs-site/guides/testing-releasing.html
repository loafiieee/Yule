Testing and releasing

Use the guarded native runners for regression coverage, then complete the in-game and two-client acceptance matrix. Build a versioned channel only from the verified binaries, publish payloads before the channel pointer, and deploy the matching server protocol.

Automated baseline

Close the game and run these from the repository root in PowerShell:

powershell -NoProfile -ExecutionPolicy Bypass -File tests/run_core_native_tests.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tests/run_v2_map_test.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tests/run_map_script_test.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tests/run_updater_test.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tests/run_update_helper_test.ps1
RunnerCoverage
run_core_native_tests.ps1Credential handling, TCP/control protocol, floating-point control, rollback envelope/schema/serializer, window/static integration, Discord IPC, LFG bot and redirect tests.
run_v2_map_test.ps1V2 parser/package fixture, native-layout atlas safety, registry retirement, collision/force/sensor behavior, native underlay/mirroring, generated-map render bridge, deterministic map script integration, rollback state, and online readiness.
run_map_script_test.ps1Isolated deterministic VM sandbox, contact phases/sensors, visual offsets, rollback replay, faults, and checked-in spring behavior.
run_updater_test.ps1Manifest parser, hashes, transactions, recovery, and loopback HTTP download/apply in disposable directories.
run_update_helper_test.ps1One-shot helper power-cut/recovery matrix, mapped-payload import audit, same-install process guard, privacy-safe recovery log, and exact relaunch argument forwarding.

A green native baseline is necessary, not sufficient: rendering, sound, state transitions, real NAT behavior, Discord desktop IPC, and process replacement still need hands-on checks.

Why the guarded runners matter

Do not run generated MinGW test executables directly. The PowerShell wrappers locate the required 32-bit MinGW/LuaJIT runtime DLLs and temporarily prepare PATH. Direct execution from an unprepared shell causes a cascade of “X.dll was not found” dialogs.
  • The test runners compile and execute isolated test binaries; they do not launch eggnoggplus.exe.
  • Do not automate launching the game during the native suite. Start it normally yourself for manual tests.
  • Updater runners use disposable roots and do not replace the live SDL2.dll.
  • If a runner reports that 32-bit MinGW is missing, install MSYS2 MinGW32 or make C:\msys64\mingw32\bin\gcc.exe available. Do not work around it by copying random DLLs into system directories.
  • Keep the game closed while compiling/replacing the installed proxy; Windows cannot replace a DLL mapped by a live process.

Two-client online acceptance

Update, rebuild, and deploy the server plus both clients from the same source first. Verify cap_client_build_gate: 1, the advertised 3/3/17 control/match/P2P tuple, and identical nonzero build=, exe=, and dll= values for both clients in the server log. Do not infer compatibility from a display version alone.

  1. Run online.troubleshoot on both machines before queueing. TCP control and UDP rendezvous should pass without freezing; the server-route adapter must match the route to the configured host.
  2. Test casual, competitive, friend challenge, request accept/decline, queue leave/change, private rematch, and duplicate actions.
  3. Cover direct routing and a restrictive/mobile/CGNAT pair that requires bounded server relay. Both clients must select the same route and leave prematch/countdown exactly once.
  4. Test normal win, loss, opponent leaving during prematch/countdown/gameplay, process close, timeout, and conflicting/stale report attempts. The remaining player gets one valid win when appropriate.
  5. Keep the native win animation visible. Return to the hub only after the game reaches main; there must be no fullscreen result overlay or hub/result loop.
  6. Use network simulation for bounded regression: dev on, then ggpo.net sim 5 2 8. Inspect prediction/rollback/correction, and clear with ggpo.net sim off.
  7. On a failure, capture net.diag, ggpo.net status, both framework logs, server logs, and both desync dumps. Do not include credentials or match keys.

Also test a deliberately old/unadvertised protocol build: it must get an update/incompatibility error before matchmaking and never be paired. See Online multiplayer.

Updater and recovery acceptance

Use a disposable copy of an installation and a test channel with a version newer than its embedded FRAMEWORK_VERSION. Cover:

  • no update, valid update, invalid JSON/schema/path, missing payload, wrong size/hash, interrupted download, and retry;
  • safe-menu handoff, exact process close, helper start, complete DLL replacement, argument-preserving relaunch, and helper exit;
  • power interruption at every replacement cut point, followed by whole-set complete-or-restore recovery;
  • committed-but-cleanup-incomplete journal recovery on the next handoff;
  • two instances attempting the same-install update;
  • ordinary command-line and --yule-uri arguments, including spaces and Unicode;
  • an already-current installation, which must not relaunch in a loop.
Never change only latest.json to paper over a bad release. Installed version comes from the binary, not the age of one dependency DLL. Keep the source version, built proxy marker, payload folder, and channel version identical.

Review mods/updater.log after each case and follow the full Updater/release guide.

Build verified Windows artifacts

  1. Close every game/updater process.
  2. Set FRAMEWORK_VERSION in update_ext.h to the new dot-separated version.
  3. Run the automated baseline.
  4. Build from the repository root in an MSYS2-capable shell:
bash compile.sh

The build compiles YuleUpdater.exe as a standalone static helper and rejects imports of replaceable payload DLLs. It then links the complete proxy to build/SDL2_test.dll before copying that exact verified artifact to SDL2.dll.

Get-FileHash .\build\SDL2_test.dll -Algorithm SHA256
Get-FileHash .\SDL2.dll -Algorithm SHA256

The hashes must match. Launch once manually for smoke testing, then close the game before packaging.

Build and publish a release channel

powershell -NoProfile -ExecutionPolicy Bypass -File tools/build_release.ps1 `
  -Version 1.2 `
  -Notes "Short user-facing release notes"

The release builder refuses a version that differs from update_ext.h or the marker embedded in the installed/built proxy. It audits required artifacts/imports and produces:

dist/
  releases/
    latest.json
    1.2/
      SDL2.dll
      lua51.dll
      libgcc_s_dw2-1.dll
      libwinpthread-1.dll
      SDL2_mixer.dll
  installer/
  EGGNOGG+_framework_installer.zip
  1. Upload the complete versioned directory (releases/1.2/) to the channel.
  2. Fetch every public payload URL and independently verify size/SHA-256 against the generated manifest.
  3. Upload latest.json atomically last.
  4. Publish the installer zip only after the live channel is valid.
  5. Test an update from the immediately previous public version and a clean install.

Do not delete an old version directory while supported clients could still be downloading it. Roll back by publishing a correctly built newer recovery release or a deliberate channel pointer backed by intact payloads; never leave the pointer referencing removed files.

Validate and deploy the online services

cd online_server
npm install
npm run check
npm test
node check_deployment.py 127.0.0.1 47778

On the production host, back up durable data and use the guarded updater from the existing online_server directory:

./update_server.sh

The script clones the configured repository/ref, locates the project layout, stages application files, preserves configured durable files such as users/ratings, restarts the systemd service, probes the actual TCP/UDP protocol, and restores the previous application if validation fails. Environment overrides include YULE_REPOSITORY_URL, YULE_REPOSITORY_REF, YULE_SERVICE_NAME, YULE_SERVER_PORT, and YULE_TARGET_ROOT.

After deploy, inspect systemctl status eggnogg, server error/output logs, public firewall/routing, and a real remote two-client match. A listening Node process alone is not a protocol-level readiness check. See Server deployment and Discord/LFG deployment.

Refresh a deployed source checkout separately

cd /home/loaf/Yule
bash ./eggnoggplus-win/tools/update_repository.sh --dry-run
bash ./eggnoggplus-win/tools/update_repository.sh

This fast-forwards the repository and updates tracked framework, documentation, test, and tooling files while preserving the complete live online_server/ directory and runtime/local state. It does not restart the service. Run online_server/update_server.sh afterward only when server deployment is intended.

Release sign-off

  • All five guarded runners pass from a clean checkout/worktree state.
  • Compiler is warning-clean and installed proxy equals the verified artifact.
  • Version agrees in source, binary marker, release folder, and channel metadata.
  • Manual UI, mod, map, music, deep-link, Discord, updater, and recovery smoke tests pass.
  • Two real current clients complete direct and relay matches; old protocol builds fail before matching.
  • Normal and disconnect results are accepted once and native win presentation completes.
  • Payload URLs/hashes verified before atomic latest.json upload.
  • Server application deploy passes syntax/tests and live TCP/UDP probe without changing durable data.
  • Logs/release archive contain no credentials, tokens, match keys, journals, user/rating databases, or local config.
  • Release notes identify migrations, compatibility breaks, known limitations, and rollback/recovery instructions.
