Installer, updater, and recovery

The installer preserves the vanilla SDL library as SDL2_real.dll and installs the framework proxy as SDL2.dll. The updater downloads asynchronously, verifies a whole release, and hands file replacement to a tiny one-shot helper after the game closes safely.

Install and uninstall

Use the packaged INSTALL.bat/install.ps1 beside or pointed at a valid Eggnogg+ copy. The installer can locate a prior receipt, move/install the game, preserve the original SDL library, install framework/runtime files, optionally register per-user yule://, create shortcuts/Steam entry, and write install.json for maintenance.

Use the packaged uninstaller rather than deleting files. It restores the original SDL2.dll, removes only installer-owned files/protocol/shortcuts, and preserves externally modified or externally owned registrations. Uninstall refuses to guess if the proxy exists but SDL2_real.dll is missing.

How in-game updates work

  1. After the first rendered frame, a worker checks the channel without blocking startup.
  2. Mods → Framework shows checking/up-to-date/update-available/error plus Check/Retry/Install and automatic update toggle.
  3. Every payload downloads into staging and is checked for exact size and SHA-256.
  4. A durable Journal V3 transaction records replacement and original identities. Status becomes verified update ready - restart.
  5. The framework waits for a safe menu—not gameplay, countdown, or an online match—then starts YuleUpdater.exe with the exact process id.
  6. The helper asks the game to close normally, verifies no second process from the same install is running, applies/reconciles the transaction, relaunches the game with ordinary arguments, and exits.

Consumed deep-link intents are not replayed. If the helper is missing/unsafe or another same-install game is running, the current game/files remain untouched and the staged transaction is retained.

Release channel schema

{
  "channel_version": 1,
  "version": "1.2",
  "base": "https://example.com/yule/releases/1.2/",
  "files": [{
    "path": "SDL2.dll",
    "sha256": "64-lowercase-hex-characters...",
    "size": 3000116,
    "overwrite": true
  }]
}

Each path is install-relative and restricted. Absolute/traversal/ADS/device/reparse escape, duplicate/colliding paths, updater recovery suffixes, and unsafe URL names are rejected. Maximum: 32 files, 128 MiB each, 256 MiB total.

mods/modframework.cfg owns auto_update (default on) and update_channel_url. HTTPS is required except explicit loopback test channels.

Publish a release safely

  1. Choose a new never-reused version and change FRAMEWORK_VERSION in update_ext.h.
  2. Close the game and updater helper. Run bash compile.sh.
  3. Build artifacts: 
    powershell -ExecutionPolicy Bypass -File .\tools\build_release.ps1 -Version 1.2 -Notes "Short release notes"
  4. Upload the complete dist/releases/1.2/ payload to a temporary server directory.
  5. Compare every public/staged file's exact size and SHA-256 with the generated manifest; atomically rename the payload directory into place.
  6. Upload the new channel as latest.json.new, validate it, then atomically rename it to latest.json last.
  7. Fetch public latest.json and every public payload once and independently verify version, size, and digest.
Never repair a release by editing only latest.json. The build tool requires its version, source version, embedded deployed DLL marker, verified test DLL hash, and updater helper to match. Restore the prior valid manifest first if a bad version was advertised.

Why YuleUpdater.exe exists

Windows cannot replace a DLL mapped by the running game. The helper exists only to close the exact process, replace files, recover an interrupted transaction, and relaunch. It is not a launcher and is excluded from update manifests.

Release packaging requires it to be self-contained and rejects imports of replaceable runtime DLLs such as Lua, MinGW runtimes, and SDL2_mixer. It opens the process before sending WM_CLOSE, waits up to two minutes, and never force-terminates the game.

Argument boundaries are forwarded directly without a shell; install root becomes the working directory. Updater logs contain bounded status, never command-line values.

Recovery behavior

Journal V3 records expected replacement and original size/SHA-256 (or absence) for every file. Before moving, the helper rehashes both sides and rejects changed originals/reparse paths. It uses write-through target-to-.old and staged-to-target moves, then validates the whole installed set before commit/backup deletion.

A partial swap rolls the whole set back. Complete interrupted sets can finish forward. Ambiguous/corrupt/missing evidence is retained and blocks launch rather than guessing. Legacy journal and adjacent .old recovery remain supported.

If a recovery dialog appears, do not delete .old, .update-recovery, or mods/update_staging. Preserve mods/updater.log and transaction evidence, then repair from a complete matching release package.

Safe verification

powershell -ExecutionPolicy Bypass -File .\tests\run_updater_test.ps1
powershell -ExecutionPolicy Bypass -File .\tests\run_update_helper_test.ps1

These guarded runners use disposable roots/loopback services, prepare required runtimes, and never replace the live DLL or launch the game. They cover manifest/hash/download, atomic apply, rollback/roll-forward, power-cut states, mapped-DLL handoff, changed originals, corrupt staging/journal, multiple instances, helper imports, cleanup, and exact argument forwarding.

For manual release acceptance, use a disposable installation and test no update, valid update, corrupt hash, interrupted download, interrupted apply, two instances, safe-menu wait, normal close/relaunch, and exact ordinary arguments. Inspect mods/updater.log for both recovery clarity and secret absence.
